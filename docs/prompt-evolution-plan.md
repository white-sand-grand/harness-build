# 提示词自进化的验证协议与复跑

验证目标是确认候选生成、独立判优和版本采用的行为是否可靠。设计依据见[设计说明](prompt-evolution-design.md)，完整课程见[提示词进化与采用](learn/11-prompt-evolution.md)。下面的提示词子系统实验与[组合运行时验收](reports/pluggable-runtime-validation.md)按各自任务和条件分别记录，不合并分数。

优化对象是系统提示词和实际启用的内置工具说明，执行记录来自 JSONL 会话和端状态评测。成功标准是正确判断改善、退化或证据不足；真实实验不预设一定提升。

| 检测对象 | 需要固定或记录什么                        | 通过条件                                                     |
| -------- | ----------------------------------------- | ------------------------------------------------------------ |
| 可信评测 | judge、受保护检查文件、实验条件与实际请求 | 改评分器不能抬分；检查资产变化使结果无效；不相容实验不可判优 |
| 候选生成 | 单组件范围、结构化假设、引用与模板变量    | 越界与无依据候选被拒绝；无失败不调用优化模型                 |
| 优化编排 | 预算、父子关系、独立选择与 heldout 审计   | 改善才保留；退化拒绝；中断仍保留证据                         |
| 执行环境 | 独立工作区/home、平台与 shell、完整测试   | 确认检查真正执行，工具子进程不继承测试凭据                   |
| 版本采用 | artifact、文件 hash 与新 run 的实际输入   | 加载内容一致，新 run 使用选定版本；不自动覆盖默认提示词      |

真实验收使用独立 MH_HOME 与工作区，凭据仅交给临时进程。先测试当前提示词的真实基线；若开发任务全通过，再以明确标记的受控缺陷起点验证候选生成与拒绝/采用流程，不把这种修复宣传为超越正常基线的收益。最终审计数据不输入优化模型。

原始运行数据保存在本机被忽略的 `evals/runs/` 目录，测试输出给出具体路径。默认提示词的采用通过显式选择候选完成。

## Step 真实验收

任务模型、优化模型与 judge 均为 **step-5-preview**，使用阶跃 Anthropic Messages 兼容端点；原生 Windows 执行，`repeat=2`、`concurrency=2`。调用前实际运行 npm 子测试，确认环境可执行且工具子进程不继承测试的模型凭据。Judge 遵循模型配置的输出预算，判决不完整时不计为可靠通过。

| 实验               | 开发集                 | 新一轮开发确认         | 最终 heldout        | 结论                            |
| ------------------ | ---------------------- | ---------------------- | ------------------- | ------------------------------- |
| 正常提示词         | 10/10                  | 无新候选，无需确认     | 6/6                 | 保留原版，无依据时不调用优化器  |
| 受控 ACK_ONLY 起点 | 基线 0/10 → 候选 10/10 | 基线 0/10 → 候选 10/10 | 基线 0/6 → 候选 6/6 | `recommend`，真实验收进程退出 0 |

受控起点明确要求固定应答、禁止工具调用，用于验证提示词改写能否影响真实执行。候选由 Step 根据十次失败轨迹生成，修改仅限 `system.md`；其规则通用，不包含任务名或答案。优化器用 9 次模型调用产出候选，随后由外部检查、配对确认和独立审计判断。另一次“无需继续修改”的分析没有产生付费优化调用。

正常实验消耗 actor 110 次、judge 2 次，报告用量 358550 token；受控修复实验消耗 actor 196 次、optimizer 9 次、judge 4 次，报告用量 723236 token。两组均完整报告用量；未配置可靠价格，因此费用为未知。这些数字描述有效验收实验的资源消耗，不代表整个开发过程的费用，也不作为性能提升结论。

短版“只应答”起点曾被模型多数忽略，仅出现一次开发失败；系统按两条失败依据的门槛停止。这说明受控缺陷必须先验证确实触发，不能只凭提示词文字认定已经退化。环境、判决预算及受控起点的预验收记录均保留；有效结果使用修复后冻结的实验条件。

正常基线复用前核对任务、源码、模型、评分器、环境和提示词 hash，以及结果全集与成功状态；复用不再次调用模型。Heldout 输出不输入优化器。受控修复证明闭环可执行，不代表超越正常基线；8 个小任务和两次重复也不能证明广泛泛化能力。

## 复跑

在项目根目录的 PowerShell 7 中，先在本机为临时进程设置 `ANTHROPIC_API_KEY`，再执行：

```powershell
$env:MH_LIVE_EVOLUTION = "1"
node --test --test-reporter=tap test/live/evolution.test.ts
```

WSL Ubuntu bash 中使用 `MH_LIVE_EVOLUTION=1 node --test --test-reporter=tap test/live/evolution.test.ts`，并在该环境配置同名凭据。独立开关避免普通 live 套件额外启动整组优化实验。正常实验上限为 240 次模型调用、100 万报告 token、750 秒；受控实验上限为 360 次调用、150 万报告 token、900 秒。

验证其他 Anthropic 兼容服务时，显式设置 `MH_LIVE_EVOLUTION_BASE_URL`、`MH_LIVE_MODEL` 和 `MH_LIVE_EVOLUTION_API_KEY_ENV`（例如 `KIMI_API_KEY`）。模型 ID 应先从服务目录核实；自定义凭据必须配合显式端点，以免误用默认的 Step 地址。每个服务使用独立输出目录，鉴权失败时不能把连通性检查当作任务验收。

## Kimi 补充验收

2026-11-10 使用 **kimi-k3.1-pro-highspeed**，端点为 `https://api.moonshot.cn/anthropic`。模型目录和实际 SSE 返回的模型标识均已核对，沿用同一套任务、两次重复及独立工作区。

正常提示词的 dev **10/10**、heldout **6/6**，系统保留原版。受控起点 dev 为 **0/10**，Kimi 生成了合法的单组件候选；复测中 5 次完成并通过，另外 5 次被服务端 HTTP 401 中断，后续优化调用也被拒绝。独立的模型目录复查同样返回 401。

该受控实验记录为 `inconclusive`，没有推荐候选，也没有执行新的配对确认或最终 heldout 审计。鉴权错误不能归因为提示词质量。

恢复鉴权后在新目录完整重跑：正常基线 dev **10/10**、heldout **6/6**；受控基线 dev **0/10**、候选 **10/10**；新一轮配对确认仍为 **0/10 → 10/10**；最终 heldout **0/6 → 6/6**。程序输出 `recommend`、`audit:passed`，进程退出 0。有效正常实验报告 173888 token，受控全流程报告 392510 token；费用未知。旧运行没有拼接进新成绩。

完整方法、失败处理、资源口径和逐次证据集中在[提示词子系统报告](reports/prompt-evolution-validation.md)；profile 冻结、worker 隔离与产物采用后的真实检查见[组合运行时报告](reports/pluggable-runtime-validation.md)。源码学习入口见[第十一章](learn/11-prompt-evolution.md)。
