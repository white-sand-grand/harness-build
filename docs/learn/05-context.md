# 05 · 让长任务保留有用的上下文

[学习路线](README.md) · 上一章：[会话与恢复](04-sessions.md) · 下一章：[检查反馈](06-feedback.md)

把所有记录保存下来解决了恢复问题，但每次全部发送给模型会越来越昂贵，也可能超过窗口。上下文管理要回答：这一轮需要哪些信息，哪些可以先放回文件？

## 先稳定每一轮共有的背景

系统提示按“基本工作方式 → 项目说明 → 记忆索引 → 环境信息”的顺序组装。项目说明来自全局 `MH_HOME/AGENTS.md` 以及 Git 根目录到当前目录沿途的说明文件；项目目录优先用 `AGENTS.md`，缺失时回退到 `CLAUDE.md`。

[buildAgent](../../src/app/build-agent.ts) 用会话对象缓存组装结果，日期只精确到天。相同会话对象的多轮请求保持相同背景，有利于保持前缀稳定；真实缓存命中仍由服务端决定。重新启动后续接会重新组装，因此缓存并不是永久保存的系统提示。

这个选择也有代价：会话中修改了说明文件或记忆索引，已缓存的系统提示不会立即更新。模型可以主动读取新文件，新会话实例会重新加载。

## 冻结背景怎样帮助服务端缓存

上面的会话对象缓存保存的是组装后的字符串。模型服务端的提示缓存则复用相同前缀的计算结果；`store: false` 也不表示关闭这种缓存。保持字符串稳定是前提，实际是否命中还取决于模型、端点、缓存寿命和前缀长度。

对 `gpt-6.1-sol`，[systemCacheBoundary](../../src/context/system-prompt.ts) 找到项目指令之后、记忆和环境之前的字符边界。应用层把边界经内核传给适配器，底层模型接口只按这个偏移划分文本，不需要理解应用的 Markdown 格式。

```text
稳定工具定义
  → developer：基本提示 + 项目指令 [缓存断点]
  → developer 的后续内容：记忆索引 + 环境
  → 历史消息与结果，末尾追加新消息
```

显式断点保护稳定背景；implicit 模式继续缓存增长的对话。已有加密推理和原生输出也原样重放，Sol 使用 `all_turns` 保持兼容推理上下文。断点前的可缓存前缀至少需要 1024 个可见输入 token；程序不会为了达到阈值填充无用文字。

清理旧输出和生成摘要会改写历史前缀，可能降低缓存复用。这是控制上下文长度的代价，需要一起观察窗口压力、缓存命中和任务结果。原厂依据、兼容网关配置及复跑命令见[提示缓存排查指南](../prompt-caching.md)。

## 长输出先放到文件里

例如测试命令输出了 5000 行，只需要其中几处错误就能继续工作。[offloadHook](../../src/context/offload.ts) 在文本超过 30000 字符或 2000 行时，把工具返回文本写入会话 `offload/`，回传头尾、删减数量和完整路径。

这让模型先看到概况，需要细节时通过 read 分段读取。图片内容仍然保留。

这里有两道不同的长度保护：进程层收集 shell 输出时先设约 1000 万字符的内存上限，超过时已经丢弃中段；offload 再保存工具返回文本。因此转存文件不能找回进程层已丢弃的内容。需要完整超大日志时，应在命令中重定向到文件。

## 旧结果清理与摘要怎样选择

下面是默认策略，阈值可在配置中调整：

| 估算用量           | 操作                                             | 是否调用模型 |
| ------------------ | ------------------------------------------------ | ------------ |
| 低于窗口 60%       | 保持当前消息                                     | 否           |
| 达到 60%，低于 80% | 清理较早、超过 1000 字符的工具结果，近期结果保留 | 否           |
| 达到 80%           | 总结较早对话，接上近期消息                       | 是           |

实现先判断摘要阈值，再判断清理阈值。因此一次很大的结果也可能直接触发摘要，不会保证先清理一轮。近期内容默认按约 20000 token 的目标保留，实际切分还要服从消息边界。

清理用占位文字替换大结果，告诉模型可以重新执行工具；原会话里的旧内容还在。摘要则把此前任务、发现和待办压成更短文本，再附上原记录路径。

## 压缩时最容易破坏什么

工具调用和工具结果必须配对。切分后如果第一条保留消息是一个没有对应调用的 `toolResult`，下次请求可能被服务拒绝。

[findCutPoint](../../src/context/compaction.ts) 从近期向前估算保留范围，优先选择用户消息边界；长工具循环没有后续用户消息时，保留完整的助手调用与结果批次。

摘要请求关闭工具和 thinking，使用单独的 [compact 提示词](../../prompts/compact.md)。摘要出错、中断或为空时不替换原消息；成功时记录摘要和保留起点，用第四章的恢复逻辑重建相同上下文。摘要请求本身的用量也进入 trace。

主请求仍可能因为估算偏差或端点限制而溢出。内核识别后会要求强制压缩，得到替换内容才重新请求；这类溢出恢复在一次运行中最多尝试一次，避免反复失败。

## 估算的边界

[tokens.ts](../../src/context/tokens.ts) 优先利用上次 API 用量，再加上新消息估算；没有用量时用内容长度近似计算。替换上下文后清除旧用量，避免沿用压缩前的基数。

这只是控制策略，不是精确 tokenizer，也不保证覆盖系统提示、工具和协议的全部开销。窗口配置过大、日志突然增长或摘要遗漏事实，仍然会影响结果。真实计费用量和价格统计采用 API 数据与配置。

## 怎样验证这一步

在项目根目录的 PowerShell 7 或 WSL Ubuntu bash 中执行：

```sh
node --import ./test/helpers/setup.ts --test test/unit/context/context.test.ts test/unit/ai/cache.test.ts
```

重点看 `cut point never separates toolCall from toolResult`、`summary failure leaves context unchanged` 和 `rebuild after compaction matches live context`。测试用小窗口和固定摘要触发边界，检查算法行为；它不证明生成摘要保留了所有语义。

源码阅读顺序：[system-prompt.ts](../../src/context/system-prompt.ts) → [offload.ts](../../src/context/offload.ts) → [compaction.ts](../../src/context/compaction.ts) → [tokens.ts](../../src/context/tokens.ts)。
