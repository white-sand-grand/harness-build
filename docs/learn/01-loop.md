# 01 · 让模型和工具形成循环

[学习路线](README.md) · 下一章：[工具与执行边界](02-tools.md)

这一章只解决一个问题：模型说“我要读这个文件”之后，谁来执行，执行结果又怎样影响下一次回答？

## 从一次模型请求开始

普通聊天可以是“发出问题 → 得到回答”。编码任务往往需要先看文件，再跑测试，最后修改并验证。模型返回的内容因此有两种：给用户看的文字，以及交给程序执行的工具调用。

工具调用可以理解为一张请求单，例如：

```json
{ "type": "toolCall", "id": "read-1", "name": "read", "args": { "path": "answer.txt" } }
```

模型只提出请求。程序找到 `read` 的实现，执行它，再把带有相同调用 ID 的结果放回对话中。

```text
user        读取 answer.txt 并告诉我内容。
assistant   调用 read，ID 为 read-1
toolResult  read-1 的结果是 42
assistant   answer.txt 的内容是 42。
```

ID 用于把请求和结果配对。文件内容通过 `toolResult` 进入后续请求，模型才有条件基于实际结果继续回答。

## 运行一个不需要密钥的例子

在项目根目录的 PowerShell 7 或 WSL Ubuntu bash 中执行：

```sh
node docs/learn/examples/loop.ts
```

输出应为：

```text
[1] 请求模型
    调用 read {"path":"answer.txt"}
    结果 42
[2] 请求模型
    回复 answer.txt 的内容是 42。
结束：done
```

[示例源码](examples/loop.ts)直接调用项目的 `runAgent`。模型由固定脚本替代，文件存在内存中，方便观察确定的执行顺序。第二次请求会断言收到对应的工具结果；最后检查两次模型调用和完整的消息顺序。

这个例子验证循环的连接方式。真实模型是否会选择正确工具，要通过后续真实模型测试和任务评测判断。

## 循环里保留哪些工作

下面是方便阅读的伪代码，完整错误与中断处理见源码：

```text
重复：
    检查中断和轮数预算
    在请求前处理上下文
    请求模型，把完整回复追加到消息列表
    如果有工具调用：
        校验、检查权限、顺序执行
        每个结果都追加到消息列表
        接收用户排队的新输入，继续下一轮
    否则：
        处理新输入、输出长度限制和结束检查
        需要继续就追加反馈，否则结束
```

循环接收 `Provider`、`Tool[]` 和 `Hooks`。这些都是接口：真实模型、固定回复模型、磁盘工具或内存工具可以使用同一个循环。文件保存和终端输出通过事件交给外层，内核无需知道日志写在哪里、界面如何显示。

## 停止比 while 循环多了什么

| 情况                   | 当前行为                               | 为什么需要                           |
| ---------------------- | -------------------------------------- | ------------------------------------ |
| 多个工具调用           | 按顺序执行，再请求模型                 | 写文件后再测试，执行顺序直接影响结果 |
| 工具名或参数错误       | 生成错误结果交回模型                   | 让下一轮有机会修正请求               |
| 模型输出被截断         | 追加继续回答的提示                     | 截断不等于任务结束                   |
| 模型准备结束但检查失败 | `onStop` 可以要求继续                  | 把验证结果纳入执行过程               |
| 运行中收到新输入       | 在工具批次结束或最终回复后接入         | 用户可以补充要求                     |
| 中断或轮数耗尽         | 返回明确结束原因，已记录的调用补齐结果 | 避免无限循环或留下悬空调用           |

`done` 只表示循环正常结束。业务上的检查是否最终通过，还取决于 hooks 和外部验证，第六章会详细说明。

## 怎样验证这一步

在项目根目录执行：

```sh
node --import ./test/helpers/setup.ts --test test/unit/agent/loop.test.ts
```

重点看三个测试：`executes tool call and feeds result back` 检查下一次请求里是否有结果；`beforeTool deny → error result with reason, tool not executed` 检查拒绝后确实没有执行；`steering queued during a final text response starts another turn` 检查最后阶段的新输入没有丢失。

思考题：如果把示例中的 `maxTurns` 改成 1，为什么工具仍然会执行，而最后没有自然语言回答？答案在循环检查预算的位置：下一轮开始前停止，当前轮的调用和结果仍然完成配对。动手修改后，结束原因会变成 `maxTurns`，原来期待正常完成和两次请求的断言也会失败；验证新行为时应相应调整这些预期。
