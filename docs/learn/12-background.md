# 12 · 用短 run 接成持续工作

[学习路线](README.md) · 上一章：[提示词进化与采用](11-prompt-evolution.md)

检查失败时通知，结果没变时保持安静，需要改文件时等待准确批准。第二天重启后，agent 还能接着做。这需要保存“下一步为什么被唤醒、哪些动作已经执行、什么已经告诉用户”。

先运行实际程序。**WSL Ubuntu / Windows PowerShell 7，项目根目录：**

```sh
node docs/learn/examples/background.ts
```

模型回复固定，SQLite、会话、文件与审批都是真的，数据只在临时目录中。先看事件和 timer 如何到达同一个 worker，再看准确的 write 如何跨 run 继续。

| 需要回答的问题     | 宿主保存什么                     | 模型拿到什么                   |
| ------------------ | -------------------------------- | ------------------------------ |
| 还有什么待办？     | Inbox 的来源 ID、顺序与消费状态  | 本次合批的事件                 |
| 什么时间再看？     | 独立 timer、UTC 到期、generation | 到期后的一条事件               |
| 上次做到哪？       | 任务状态、进展、原始 session     | 有界进展与按需记忆索引         |
| 哪个修改获准？     | 准确调用、文件前置内容与实现指纹 | 工具执行结果；数据不能替代授权 |
| 已经告诉用户了吗？ | Outbox、投递回执与已读           | 最近实际投递的摘要             |

`runAgent` 仍是纯循环。新增的 defer 只返回一个纯数据批次，再等待应用注入的持久化回调。数据库、定时器、审批卡与投递留在 app，CLI/桌面决定怎么呈现。

## 一次批准为什么需要原始日志

A 读取成功、B 等待修改、C 尚未读回。批准 B 后写入成功；接下来读了一个很长的日志，模型上下文发生压缩。如果用压缩后的 messages 寻找 B 的完成证据，结果可能已不在里面。

当前实现按原 assistant entry，在原始 SessionEntry 中匹配准确工具名与 ID；遇到后续同 ID 的新调用就停止关联。模型需要的是精简上下文，恢复与权限需要的是可靠记录。这两种需要由不同数据表示承担。

## 连续工作怎样进入进化闭环

持续任务提供可靠的失败记录，维护作业再决定是否值得开始实验。evolution handler 在更高层注入，因此 app 不反向依赖 eval；证据不足时不用调用优化模型。入围候选仍经过新鲜配对确认和 heldout 审计，采用需要显式选择。

dream 整理已完成会话的笔记；任务状态与投递记录由宿主管理，不能交给 dream 改写。记忆更新可影响下一 run 的召回，但不能变成新的文件授权。
