# 02 · 把请求单接到真实工具

[学习路线](README.md) · 上一章：[核心循环](01-loop.md) · 下一章：[模型接口](03-providers.md)

有了循环，下一步是把“读一个文件”“替换一段代码”“运行测试”接到操作系统。这里既要给模型足够清楚的接口，也要处理失败、超时和操作范围。

## 一个工具有两部分

第一部分是给模型看的：名称、说明和参数格式。第二部分是给程序执行的：`execute(args, context)`。二者在 [Tool 接口](../../src/agent/types.ts)中连接。

模型只收到前一部分，不会收到执行函数。循环拿到调用后，用 [validateCall](../../src/agent/validate.ts) 检查参数，再执行权限 hook 和工具。参数校验不会把字符串 `"30"` 自动转成数字 `30`；错误会回传，让模型重新发出正确请求。

工具结果也分为两个用途：

| 字段                 | 谁读取         | 例子                         |
| -------------------- | -------------- | ---------------------------- |
| `content`、`isError` | 模型和调用方   | 文件文字、执行状态、失败提示 |
| `details`            | 界面和执行记录 | 编辑 diff、字节数、截断标记  |

这样可以把必要结果放进上下文，把展示细节交给外层，减少每轮重复发送的内容。

## 四个工具怎样配合

以修复求和函数为例，一个可能的调用过程是：read 读取源码 → bash 运行测试 → edit 修改循环边界 → bash 再次测试。实际顺序由模型选择，下面讲的是各工具的契约。

| 工具    | 对应实现                             | 设计重点                                                                    |
| ------- | ------------------------------------ | --------------------------------------------------------------------------- |
| `read`  | [read.ts](../../src/tools/read.ts)   | 行号方便定位；`offset`/`limit` 支持分段读取；目录和二进制文件给出下一步提示 |
| `write` | [write.ts](../../src/tools/write.ts) | 创建父目录，适合新文件或整体覆盖，报告写入情况                              |
| `edit`  | [edit.ts](../../src/tools/edit.ts)   | 精确匹配旧文字，多处匹配需要上下文或 `replaceAll`；保留换行格式和 BOM       |
| `bash`  | [bash.ts](../../src/tools/bash.ts)   | 利用已有命令搜索和测试，返回输出、退出码、超时和中断状态                    |

只保留这四种接口，是因为文件搜索、Git、构建工具已经能通过命令行使用。代价是 shell 命令会受到平台差异影响，也无法像专门工具一样提供细粒度参数约束。

工具说明单独放在 [prompts/tools](../../prompts/tools)，因此可以对说明做实验，而不修改执行逻辑。参数结构仍由代码定义。

## 错误需要告诉模型下一步怎么做

例如模型尝试把 `return 0` 替换为 `return total`，但文件里出现两处。edit 会报告匹配数量和位置，要求补充周围文字或明确替换全部，不会猜测用户想改哪一处。

其他典型情况包括：文件不存在时指出当前目录；复制 read 输出中的行号导致匹配失败时提示移除前缀；参数 JSON 不完整时要求重新发送完整对象。

预期内的工具失败使用 `ToolError`；意外异常带上 `Internal tool error:` 前缀。两者都会进入工具结果，调用方可以追查，模型也有机会继续。

命令返回非零退出码则直接写入输出和状态，**不会自动设置工具结果的 `isError`**。例如测试失败是模型需要阅读的业务结果。分析执行记录时，不能把“工具错误数为零”当作“所有命令都成功”。

## 执行边界放在哪里

[permissionHook](../../src/hooks/permission.ts) 在执行之前工作：普通读取放行；write/edit 解析真实路径后判断目录范围；bash 按危险模式检查。需要询问时可以批准一次、批准本会话同类操作或拒绝。没有人可以回答时，风险操作被拒绝。

路径会解析符号链接和 Windows junction，防止表面在项目内、实际写到项目外。dream/analyze 还有严格输出目录约束，`--yolo` 也不会解除它们。

这套设计用于防误操作。shell 可以运行任意程序，命令字符串的模式检查也有绕过方式，所以这些规则没有提供操作系统级隔离。

## 为什么命令结束了，子进程还可能在运行

测试命令可能再启动多个进程。只终止最外层 shell，后代可能继续占用端口，或者让输出管道一直不关闭。

[runCommand](../../src/util/process.ts) 统一管理这些情况：

- Linux/macOS/WSL 用进程组，超时或中断时先发 SIGTERM，必要时再发 SIGKILL。
- Windows 用 [Job Object 运行器](../../src/util/windows-job.ps1)管理 shell 和后代，结束时清理组内进程。
- 每次调用使用显式 `cwd`，关闭标准输入；默认 120 秒超时，bash 工具允许最多 600 秒。
- Windows 选择 Git Bash → PowerShell 7（`pwsh.exe`）→ Windows PowerShell 5.1（`powershell.exe`），工具描述告诉模型当前语法。

每次调用都会启动新 shell，因此前一次的 `cd` 和临时变量不会延续。这牺牲了持续终端状态，但能减少不同调用之间隐藏的依赖。进程收集输出另有内存上限；超大日志应由命令重定向到文件。

## 怎样验证这一步

在项目根目录的 PowerShell 7 或 WSL Ubuntu bash 中执行：

```sh
node --import ./test/helpers/setup.ts --test test/unit/tools/tools.test.ts test/unit/hooks/permission.test.ts test/unit/tools/process-tree.test.ts test/unit/tools/windows-pipeline.test.ts
```

在测试中跟踪“失败后发生了什么”：多处匹配是否拒绝；越界链接是否触发询问；超时后不响应 SIGTERM 的后代是否终止。Windows 管道的实际执行案例只在原生 Windows 下运行，WSL 的通过结果不能代替它。

思考题：如果想并行执行所有工具，`edit → bash 测试` 这个顺序会发生什么？是否只标记 `readOnly` 就足以判断任意工具之间没有依赖？
