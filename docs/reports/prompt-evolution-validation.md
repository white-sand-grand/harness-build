# 提示词自进化真实验证报告

验证日期：2026-11-09 至 2026-11-10（Asia/Shanghai）。本报告区分正常任务能力、受控提示词修复，以及执行故障。公开证据为[逐次结果与实验指纹](evidence/2026-11-10-prompt-evolution.json)；原始会话、请求快照和工作区保存在本机被忽略的运行目录。

## 验证什么

验证模型能否使用 mini-harness 完成任务，以及能否根据重复失败改写一份有缺陷的系统提示词，并通过独立检查。这里没有训练模型权重，也没有根据 heldout 题目修改提示词或答案。

正常提示词已通过的任务不能凭重复通过就宣称“优化收益”。因此另设受控实验：起点 `ACK_ONLY` 要求固定应答、禁止工具调用。只有观察到真实失败，才让优化器依据 dev 轨迹提出修改。

## 固定条件与成功标准

| 条件      | 设置                                                                                             |
| --------- | ------------------------------------------------------------------------------------------------ |
| 环境      | 原生 Windows Node 24、Git Bash、独立工作区和 MH_HOME                                             |
| 任务      | 5 个 dev、3 个 heldout；每题重复 2 次，并发 2                                                    |
| Step 模型 | `step-5-preview`，任务、优化器与 judge 使用相同模型                                              |
| Kimi 模型 | `kimi-k3.1-pro-highspeed`，模型目录与实际服务响应均已核对                                        |
| 协议      | Anthropic Messages SSE；Step 使用阶跃兼容端点，Kimi 使用 Moonshot 国内兼容端点                   |
| 修改范围  | 每次只允许修改 `system.md`；其他提示词、评分器与独立检查资产固定                                 |
| 搜索预算  | 正常实验：240 次 provider 调用、100 万报告 token、750 秒；受控实验：360 次、150 万 token、900 秒 |
| 输出预算  | 各模型配置为 8192；judge 使用同一模型配置的上限                                                  |
| 判优规则  | dev 配对改善且无退化，重新运行基线/候选确认，再做最终 heldout 审计                               |

每次任务的 `status` 与 `endReason` 分开记录；只有检查通过且正常结束才构成可靠成功。网络或鉴权错误、判决无效、检查资产被改动、结果缺失或实验条件不一致，均不能成为候选晋级依据。

运行清单保存任务/fixture、评分器、源码、有效配置、运行时与关键环境 hash。真实请求另外保存 system/tools 快照。公开 JSON 只导出白名单字段，保留每份原始 results 文件的 SHA-256；它足以核对本报告统计与逐次结果，但不等同于公开完整私有执行环境。

## Step 的完整结果

| 阶段                  | 原版或受控基线 |     候选 |
| --------------------- | -------------: | -------: |
| 正常 dev              |          10/10 | 无需生成 |
| 正常 heldout          |            6/6 | 无需生成 |
| 受控 dev              |           0/10 |    10/10 |
| 新一轮 dev 配对确认   |           0/10 |    10/10 |
| 受控最终 heldout 审计 |            0/6 |      6/6 |

正常实验输出 `unchanged`，没有调用优化模型。受控实验输出 `recommend`、`audit:passed`，真实验收进程退出 0。

优化器引用十次失败的事件，识别出 ACK_ONLY 禁止工具执行的共同原因，并生成[通用编码指令](evidence/step-controlled-system.txt)。候选要求读文件、实际修改、运行验证与报告结果，不包含评测任务名或答案。它经过任务执行与配对确认后才被推荐，默认提示词未自动替换。

## Kimi 的结果

| 阶段                  | 原版或受控基线 |     候选 |
| --------------------- | -------------: | -------: |
| 正常 dev              |          10/10 | 无需生成 |
| 正常 heldout          |            6/6 | 无需生成 |
| 受控 dev              |           0/10 |    10/10 |
| 新一轮 dev 配对确认   |           0/10 |    10/10 |
| 受控最终 heldout 审计 |            0/6 |      6/6 |

有效重跑同样输出 `recommend`、`audit:passed`，进程退出 0。Kimi 根据八条失败事件引用，生成[简短的工作区任务指令](evidence/kimi-controlled-system.txt)：要求读取相关文件、实际完成修改、控制修改范围、执行验证。候选未包含具体题名或答案，任务、检查与评分规则保持固定。

首次运行正常基线也为 16/16，但受控候选复测中途开始返回 HTTP 401，五次任务因此中断，后续优化调用也被拒绝。该实验保持 `inconclusive`，逐次结果单独列在证据中的 `kimi-interrupted`，不计入有效候选成绩。

恢复鉴权后重新完整执行基线与受控实验。旧基线因环境指纹不同没有被复用，校验在模型调用前拒绝，之后使用全新运行目录。没有把旧运行的成功项补到新运行，也没有把鉴权故障当成提示词缺陷。

## 资源统计口径

| 有效实验                    | actor 调用 | optimizer 调用 | judge 调用 | 报告 token |
| --------------------------- | ---------: | -------------: | ---------: | ---------: |
| Step 正常基线               |        110 |              0 |          2 |     358550 |
| Step 受控修复全流程         |        196 |              9 |          4 |     723236 |
| Kimi 有效重跑正常基线       |         76 |              0 |          2 |     173888 |
| Kimi 有效重跑受控修复全流程 |        151 |              5 |          4 |     392510 |

Actor 包含任务循环及可能的摘要；一次 provider 调用可能在内部发生 HTTP 重试。Token 合计为普通输入、输出、缓存读取和缓存写入的报告数总和，不把缓存命中当作任务成功。缺少可靠价格配置，费用为未知。

表格描述所列有效实验，不包含所有开发、探测、失败或中断调用的总费用。不同服务的随机采样、时间与运行过程不同，本报告不据此给模型排名，也不以 token 差异宣称性能改善。

## 保留下来的失败及其影响

| 现象                                               | 处理与结论                                                                        |
| -------------------------------------------------- | --------------------------------------------------------------------------------- |
| 临时 Windows 环境遗漏 PATHEXT，npm 后代找不到 Node | 修正验收启动环境并增加 npm 子测试；旧运行保持无效，关键环境纳入比较指纹           |
| Step judge 用满原固定的 2048 token 上限却没有 JSON | 改为尊重模型配置，增加预算耗尽回归；评分标准不变，旧运行没有记成通过              |
| 短版“禁止工具”起点只有一次真实 dev 失败            | 不足两条依据时停止；改用先验证确实触发失败的明确 ACK_ONLY 起点                    |
| Kimi 首轮在候选执行中途出现连续 HTTP 401           | 记录为 `inconclusive`，没有推荐或审计；重试使用独立运行，不将中断数据拼成成功结果 |
| 旧基线的执行环境与新进程不同                       | 拒绝复用，重新运行完整基线                                                        |

这些修补针对协议、实验环境和证据可信度，没有针对 heldout 失败调整 actor 提示词。可重复的离线测试同时覆盖退化拒绝、无效 judge、偶然提升、重复候选、预算耗尽、中断和严格读取范围。

## 如何复跑

先在本机临时进程环境中配置服务凭据，密钥不要写进源码或命令示例。Windows 使用 PowerShell 7，从项目根目录运行 Step：

```powershell
$env:MH_LIVE_EVOLUTION = "1"
$env:MH_LIVE_MODEL = "step-5-preview"
$env:MH_LIVE_EVOLUTION_BASE_URL = "https://api.stepfun.com/step_plan/v1/messages"
$env:MH_LIVE_EVOLUTION_API_KEY_ENV = "ANTHROPIC_API_KEY"
node --test --test-reporter=tap test/live/evolution.test.ts
```

Step 默认读取 `ANTHROPIC_API_KEY`。Kimi 使用 `KIMI_API_KEY`，同一目录运行：

```powershell
$env:MH_LIVE_EVOLUTION = "1"
$env:MH_LIVE_MODEL = "kimi-k3.1-pro-highspeed"
$env:MH_LIVE_EVOLUTION_BASE_URL = "https://api.moonshot.cn/anthropic"
$env:MH_LIVE_EVOLUTION_API_KEY_ENV = "KIMI_API_KEY"
node --test --test-reporter=tap test/live/evolution.test.ts
```

WSL Ubuntu bash 中设置同名变量，再执行相同 Node 命令。每个运行使用新的输出目录；`MH_LIVE_EVOLUTION_OUTPUT` 可指定位置。测试将凭据从环境读入局部内存并删除环境值，再通过 provider 私有字段认证；npm 子测试验证工具进程不继承这些凭据。

两个协议端点均需账户真实拥有对应模型。404、401 或权限不足应先处理连接，不能替换成其他模型却仍沿用原模型名称报告。鉴权恢复后的重跑保持旧失败数据，费用与重试次数另行说明。

## 本地检查与公开证据

WSL 的 `pnpm check` 通过类型、分层、格式、288 项离线测试与构建；原 288 项测试清单保留，8 个任务的初始和参考修改状态通过检查。原生 Windows 全量测试以 `--test-concurrency=1` 运行，289/289 通过，另外包含 Windows 进程管道行为，0 failed / 0 skipped。

与真实模型并行运行的 Windows 检查曾在进程终止测试中遇到 PID 文件尚未生成的启动时序失败。相同测试单独运行通过，最终完整串行运行也通过；没有扩大超时或修改断言。这个记录提示进程相关测试仍受机器负载影响，不能把一次并行通过等同于任意负载下的稳定性保证。

公开 JSON 包含 6 组实验、20 个结果行齐全的执行阶段；结果行齐全不等于执行成功。每个阶段列出预期尝试数、实际逐次结果、可靠通过数和不可变实验指纹；其中明确保留首次 Kimi 的正常基线与 401 中断实验。它不包含 API 请求头、密钥、私有绝对路径或原始会话。两个生成后的候选文本单独公开，SHA-256 可与 JSON 对照。

报告是固定日期的真实运行记录，不是持续更新的排行榜。后续重跑应产生新记录，不能覆盖这次的失败或将未复测的修改算作已经验证。

## 结论范围

受控修复验证了“失败证据 → 修改提示词 → 实际执行 → 重新确认 → 独立审计”的工程流程。它不证明超过正常提示词的表现，也不证明一般编码任务的广泛提升。8 个种子任务、每题两次重复适合机制验收和开发回归；更强的泛化结论需要更多未参与开发的任务与重复实验。
